# R2 media implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make uploaded VODs and saved clips durable in private R2, retain Supabase media reads during migration, and control retention and media cost.

**Architecture:** A feature-gated S3-compatible R2 adapter serves direct multipart VOD uploads and verified clip archives. Supabase remains the authority for ownership, jobs, Spark charges, provider selection, and expiry. Existing local uploads and Supabase archives remain readable. No live provider calls occur in mock tests.

**Tech Stack:** Next.js 16 Node routes, TypeScript, Supabase Postgres, Cloudflare R2 S3 API, AWS SDK for JavaScript, Node test runner.

**Spec:** `docs/superpowers/specs/2026-10-30-r2-media-design.md`

## Global constraints

- Work on `feat/vod-discovery-quality` only; no deployment, production writes, purchases, paid APIs, or customer-file deletion.
- Preserve AI, billing, Sparks, pricing, clip quality, existing uploads, and Supabase archive reads.
- R2 is opt-in and fails closed when configured incompletely; no key enters browser code or logs.
- Every storage status is confirmed by the provider before Supabase marks it available.
- Existing customer media has no automatic expiry until a separately reviewed migration.

## Review focus

- A stolen/guessed upload ID must not let another user analyze, finalize, or download its media (Task 2 tests).
- Worker death during multipart completion or archive verification must leave a retryable state, never a false `ready`/`stored` state (Tasks 2 and 4 tests).
- R2 `HEAD` success with wrong byte length or hash must not finalize a clip or migration (Tasks 4 and 5 tests).
- An active analysis/export must not have its source or scratch deleted (Tasks 3 and 6 tests).
- Provider misconfiguration must never fall back to writing media to a different provider without explicit choice (Tasks 1 and 4 tests).

### Task 6: Retention and cleanup

**Files:** Add `supabase/migrations/032_r2_media_retention.sql`; create `lib/r2-media-cleanup.ts` and tests; wire processing worker scheduler and owner-facing expiry UI.

**Interface:** New saved R2 clips receive UTC `expires_at` of 5 days (Free) or 30 days (Pro) from backup confirmation; existing clips remain grandfathered. Cleanup is claim/lease based, skips active jobs, deletes R2 objects first, records retry on failure, then marks expired. VOD multipart sessions abort after one day; completed source VODs expire only after their jobs are done and the separately defined reclip window. R2 lifecycle rules are documented as a later safety net, not silently installed.
